# Implementation plan: closing the StudioSuits gaps on suits.me

Status: Draft for owner approval. Nothing in this plan is authorized to build or remove until the owner approves it, per the agreed sequence: report first, then plan, then approval, then build.
Companion document: docs/ux-audit/studiosuits-gap-analysis.md (gap IDs below refer to that report).
Prepared: October 26, 2026.
Effort figures are planning estimates in working days for one engineer, given as ranges. They are estimates, not commitments; Wave 0 exists to shrink the uncertain ones.

## 1. Rules every package follows

1. One work package per branch and pull request. Each PR names its gap IDs, includes before and after evidence, and lists regressions checked.
2. Tests before claims: run the existing suites (catalog, suit-edits, commerce) plus any test a package adds. The commerce suite needs dependencies installed (pnpm install); a package is not done on a machine where its tests could not run.
3. No merge without explicit owner approval. A merge deploys to production.
4. No real orders, no real customer data, no invented measurements, prices, reviews, or delivery promises at any stage. Sandbox only for commerce work.
5. Removals (menu duplicates, unused code, the banned punctuation cleanup) happen only in their named packages, after this plan is approved.
6. The guest experience must keep working in every package that touches accounts, sizes, or the bag.

## 2. Codebase grounding (verified October 26, 2026)

- The storefront is vanilla JS in apps/website/public: app.js (core flows, measurement studio, drafts in localStorage via saveDraft), complete.js (completion, bag, checkout flows), expanded.js (expanded customization), merchant.js (fabric led collections), navigation.js plus generated navigation-data.js, gallery.js, quick-add.js.
- Item state already carries fields the bag does not render (for example lining is present in app.js and complete.js state), which is why CRT-01 starts with a payload check, not a rewrite.
- Catalog and navigation data are generated by scripts (generate-catalog.cjs, build-merchant-catalog.cjs, build-suit-edits.cjs, build-studio.mjs). Content changes go through the generators and their source data, never by editing generated files alone.
- Commerce server code exists (lib/commerce.ts, app/api) with a D1 database for orders; it is disabled by missing merchant configuration, not missing code.
- The page is served as one HTML file from app/route.ts (web/index.html mirrors public/index.html, guarded by a test).

## 8. Wave 4: Real pages migration

Gap: NAV-01 (with NAV-05 and part of COD-03 as passengers).

Approach, staged so it can stop safely at each stage:

1. **Spike (2 to 3 days):** prove one collection (Wool Suits) at a real URL inside the current hosting and build pipeline. Two candidate mechanics, decided by the spike: server routes in the existing framework app that render the storefront with the collection preselected, or build time generation of one HTML entry per collection from the single source. The spike report compares build time, hosting fit, and how the generated catalog scripts are affected.
2. **Redirect and compatibility layer (1 to 2 days):** every existing hash route lands on the equivalent real URL; bookmarks and any external links keep working.
3. **Rollout (3 to 5 days):** all categories and collections move, menu hrefs updated, sitemap regenerated, the two HTML copies problem retired by the chosen mechanic, or explicitly kept with its guard test if the mechanic requires it.
4. **Verification (1 to 2 days):** menu inventory parity against the pre migration inventory, catalog tests, spot journeys per category, and the SEO basics from PR #1 checked page by page.

Total estimate: 7 to 12 days. Risk: medium to high, because routing touches every page; staging it after Waves 1 to 3 means the content being routed is final, not moving. Rollback is the previous build, since no data model changes are involved.

## 9. Wave 5: Accounts and post login parity

Gaps: ACC-01, SIZ-04.

Decision needed before build: identity approach. The deployment already identifies signed in users to the commerce API through the hosting gateway (the code trusts an authenticated user header from the Sites integration). Options:

- **Option A (recommended starting point):** build on the existing gateway identity and the existing D1 database. Add profiles and orders tables keyed to that identity, add sign in and account entry points to the header, and migrate a guest's local profiles into the account on first sign in. Least new infrastructure; depends on how the hosted site exposes sign in to visitors, which Wave 0 style verification must confirm on the real deployment.
- **Option B:** a standalone email and password (plus Google) account system inside the app. More control, more security surface, more time, and it duplicates what the platform may already provide.

Build steps once the option is chosen (estimate 8 to 12 days for Option A; Option B sized separately):

1. Account entry points (header, checkout, measurement profiles) with the guest path unchanged.
2. Server storage for profiles and orders tied to the account; local profiles remain for guests.
3. Guest to account migration of local profiles and orders on first sign in, with the customer told what moved.
4. Parity checklist as the acceptance gate: same menus, listings, customization, sizing, bag, and checkout before and after login, verified journey by journey, plus account only additions (saved profiles, order history) reachable in at most one extra click.

## 10. Wave 6: Real commerce enablement

Gap: CHK-01. This is a business project with engineering support, not a UX package.

Owner and operations inputs, all required before engineering starts: Authorize.Net credentials (stored as server secrets, never in code or chat), COMMERCE_APPROVED approval, an approved shipping charge, a tax quote service or an approved tax approach, public storefront and webhook reachability (the current owner private site blocks external webhook senders, per the repo handoff notes), and fulfillment readiness for real orders.

Engineering steps (estimate 3 to 5 days once inputs exist): configure secrets and flags, run sandbox end to end (successful payment, rejected payment, duplicate submission, webhook verification, amount mismatch), verify totals, tax, and delivery in the order record, then remove demo labeling in the same PR that proves a real sandbox order. Go live (production credentials and approval) is a separate owner decision after sandbox proof.
