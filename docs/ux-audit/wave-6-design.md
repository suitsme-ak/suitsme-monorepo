# Wave 6 design and owner inputs: real commerce enablement (CHK-01)

Status: design only. No site code changes in this package. Prepared 2026-10-29 on main at 609d943 (after Wave 5 merged as PR #41). Every claim in section 0 was verified by reading the code on this tree; anything that could not be confirmed from the repo is in the unverified register in section 6, stated as unverified.

Wave 6 is gap CHK-01 from docs/ux-audit/studiosuits-gap-analysis.md: checkout on suits.me is a labelled demo and no real payment can be taken. The implementation plan (section 10) sized the engineering at 3 to 5 days once owner inputs exist, on the assumption that the remaining work is configuration, sandbox proof, and removing demo labelling. This document tests that assumption against the code as it stands after Waves 1 to 5. The short answer: the assumption mostly holds, because the Authorize.Net integration was already built before this program began. Section 1 lists what the code read found that the plan did not name, and section 4 sizes the packages with those items included.

## 0. Verified current state

### 0.1 The demo mode gate, exactly

One function decides everything: `settings(env)` in apps/website/lib/commerce.ts (line 5). It reads only server settings, never code constants:

- `live` is true only when `ANET_ENV` is exactly the string `production`. Any other value, including unset, means the sandbox endpoints.
- `ready` requires `ANET_API_LOGIN_ID`, `ANET_TRANSACTION_KEY`, `ANET_SIGNATURE_KEY` and the `DB` database binding to all be present.
- When `live` is true, `ready` additionally requires `COMMERCE_APPROVED` to be exactly `true`, a `TAX_QUOTE_URL` to be present, and `SHIPPING_CENTS` to be all digits.
- `mode` is `live` when ready and live, `sandbox` when ready and not live, and `demo` whenever not ready. There is no error state: a production configuration that is missing one item silently reports demo.

The truth table that follows from the code:

| Settings present | Mode | What checkout does |
| --- | --- | --- |
| Any ANET secret or `DB` missing | demo | Server checkout refuses with 503 and the message "Secure checkout is not enabled. You can complete a demo order instead." The client records a local demo order instead (section 0.3). |
| Three ANET secrets plus `DB`, `ANET_ENV` not `production` | sandbox | Real checkout runs against the Authorize.Net sandbox endpoints. Shipping and tax are both 0 (the totals block runs only when live, section 0.3). `COMMERCE_APPROVED` is not consulted. |
| `ANET_ENV=production` plus secrets and `DB`, but `COMMERCE_APPROVED`, `TAX_QUOTE_URL` or a numeric `SHIPPING_CENTS` missing | demo | Same as the first row. Production intent with one missing item is indistinguishable from no configuration. |
| All of the above plus `COMMERCE_APPROVED=true`, `TAX_QUOTE_URL`, numeric `SHIPPING_CENTS` | live | Real checkout against production endpoints, with shipping and tax applied. |

The client learns the mode from the public `GET /api/payment/config`, which returns `{ready, mode}` and nothing else, and renders its checkout copy from it (apps/website/public/complete.js, fetched at boot, line 177). Live verification on 2026-10-29: `GET https://suits.me/api/payment/config` returns `{"ready":false,"mode":"demo"}`. That confirms the deployed configuration does not complete any ready combination. It cannot show which individual settings are missing, and nothing in the repo can either (section 6).

### 0.2 The Authorize.Net integration as built

The whole server integration is the single dispatcher `commerce(request, env)` in lib/commerce.ts (94 lines), served by four thin route files (app/api/checkout, app/api/orders/[id], app/api/authorize/webhook, app/api/payment/config), each delegating every method to the dispatcher.

- Transport: JSON POSTs to the Authorize.Net API. Sandbox base is `https://apitest.authorize.net/xml/v1/request.api`; production base is `https://api.authorize.net/xml/v1/request.api`, chosen by `ANET_ENV`. Every call has a 20 second timeout, and a non-Ok `messages.resultCode` becomes a shopper safe error.
- Payment shape: the Accept Hosted pattern. The server calls `getHostedPaymentPageRequest` with an `authCaptureTransaction` (authorize and capture in one step) for the order total, the order id as `invoiceNumber`, the customer email, and the delivery address as `billTo`. It receives a token; the browser then POSTs that token directly to the hosted payment page (`https://test.authorize.net/payment/payment` in sandbox, `https://accept.authorize.net/payment/payment` in production). Card details are entered on Authorize.Net's page and never touch suits.me code, suits.me servers, or the suits.me database. There are no card fields anywhere in the client.
- Hosted form settings set in code: card code required, bank account payments off, receipt page shown, merchant name "Suits.me", return URL `<origin>/#payment-return` and cancel URL `<origin>/#checkout`, both built from the serving request's origin, so no storefront origin is configured anywhere.
- What is not used: no Authorize.Net SDK, no customer profiles, no tokenized repeat payments, no Apple Pay or PayPal options in code. None of those are needed for launch; they are listed so the boundary of what exists is explicit.

### 0.3 Checkout flow, end to end

1. Review step (client): the shopper confirms a consent checkbox ("I've reviewed the items, customization, and measurement profiles in this order"), without which `submitCheckout()` refuses. When the config reports not ready, the same button places a demo order instead: a `DEMO-` record written to browser local storage only, the bag cleared, no server call beyond the config read. Demo copy at this step is explicit: "This demonstration records a sample order without requesting card details or charging you."
2. When ready, the client POSTs `/api/checkout` with the bag and delivery details and an `Idempotency-Key` header. The key is generated once per bag plus delivery fingerprint and persisted in local storage (`suits-checkout-attempt`), so a retry of the same checkout reuses the same key.
3. The dispatcher first requires an owner: the shared resolver from Wave 5 package 5.6 (`resolveOwner` in lib/accounts.ts). A valid app session wins, keyed `app:<user id>`; else the gateway identity header exactly as commerce read it before Wave 5; else the request is refused 401 "Please sign in to continue." This applies to checkout and to order reads. Section 1, finding F2, covers what this means for guests at go live.
4. Origin check: the `Origin` header must equal the request origin, else 403. Body size is capped at 100 KB.
5. If `settings(env)` is not ready, 503 (the demo message above). Nothing is written.
6. Validation and server side pricing: `cleanShipping` requires a complete US delivery address (email format, state as two uppercase letters, ZIP as 5 or 5 plus 4, country exactly `US`). `cleanItems` accepts 1 to 20 items, looks each product up in the server catalog (lib/catalog.json) by index, and recomputes the price from the catalog base plus the full Wave 3 option price tables mirrored in cents at the top of commerce.ts. Client supplied prices are ignored; the suite proves a tampered price of 1 still charges the catalog amount. Measurement profiles are required for garments and validated (standard size ranges, or body values within the accepted range). Gift cards are accepted only at the six fixed amounts with recipient name and a plausible email.
7. Idempotency: an existing order for the same owner and key is reused. If it is already paid, 409 "This order has already been paid." If the stored items or shipping differ from the new request under the same key, 409 "The bag changed. Please restart checkout." A unique index on `(owner, idempotency_key)` in the database backs this, and an insert race falls back to reading the winning row.
8. Totals: only in live mode, shipping is `Number(SHIPPING_CENTS)` and tax comes from the quote call in section 0.4. In sandbox mode both stay 0. The order row is inserted into `store_orders` with status `pending` and `total_cents = subtotal + shipping + tax`. Order ids are `SM` plus 16 uppercase hex characters.
9. The server requests the hosted page token for the stored order and returns `{token, paymentUrl, orderId, totalCents}`. The client stores the order id as `suits-pending-order` and submits the token form to Authorize.Net.
10. Return: Authorize.Net sends the shopper back to `/#payment-return`. `paymentReturnPage()` reads the pending order id, fetches `GET /api/orders/:id` (owner scoped; another owner's id reads 404), and if the status is `paid` it records the order in the browser list, clears the bag, and lands on the order page. If still `pending`, it shows a "payment is being confirmed" page with the order reference and a manual Check status button. There is no automatic polling.
11. Payment confirmation arrives only through the webhook (section 0.5). Nothing on the return path marks an order paid.
12. Order visibility after payment: the owner's row is returned by `GET /api/orders/:id`, and since Wave 5 by `GET /api/account/orders` for app accounts, merged with imported demo snapshots badged as demo records. There is no staff facing view of any kind (finding F5).

`store_orders` (db/schema.ts, migration drizzle/0000_furry_hardball.sql) holds: id, owner, idempotency key, items and shipping as JSON text, subtotal, shipping, tax and total in cents, status, transaction id (nullable), created at. Unique indexes on `(owner, idempotency_key)` and on `transaction_id`. The only status values the code ever writes are `pending` and `paid`.

### 0.4 Shipping and tax as coded

- Shipping is a single flat amount in cents from the `SHIPPING_CENTS` setting, applied to every live order regardless of destination, weight, or order value. The validation accepts 0 to 100000 cents. Anything rule based is not a configuration change; it is new code, and section 2 asks the owner to say so if that is what they want.
- Tax exists only as a call to an external service the owner provides. In live mode the server POSTs `{shipping, items, subtotalCents, shippingCents}` to `TAX_QUOTE_URL` (HTTPS required, 15 second timeout, optional bearer `TAX_QUOTE_TOKEN`) and requires the reply `{taxCents}` to be a safe integer between 0 and the subtotal inclusive; anything else fails the checkout with "Invalid tax quote." No tax service, tax table, or tax rate exists anywhere in this repo. The bounds matter for the owner's choice in section 2: a quote above the merchandise subtotal is rejected by design, and whether shipping is taxed is entirely up to what the service returns, since it receives the shipping amount.
- The shopper does not see the shipping or tax figures on suits.me before paying. The review step shows the merchandise subtotal with the lines "Calculated by merchant settings" and "Calculated before payment"; the final charges first appear on the Authorize.Net hosted form. The README documents this as the intended shape ("Final delivery/tax charges appear on the hosted payment form"). Finding F3 records the decision this needs.

### 0.5 The webhook

`POST /api/authorize/webhook` is implemented, not stubbed:

- If `ANET_SIGNATURE_KEY` or `DB` is missing it answers 503. Bodies over 100 KB are refused.
- It requires an `X-ANET-Signature` header of the form `sha512=<128 hex>` and verifies an HMAC SHA-512 over the raw body. The HMAC key bytes are the UTF-8 encoding of the signature key setting, which the code first requires to be exactly 128 hex characters. Section 1, finding F4, records the limit of what this proves.
- Only the event type `net.authorize.payment.authcapture.created` is acted on; every other event is acknowledged and ignored.
- The payload is never trusted for money: the handler re-fetches the transaction from Authorize.Net (`getTransactionDetailsRequest`), reads the invoice number from the provider's own record, loads that order, and requires the provider amount to equal the stored `total_cents` exactly and the transaction status to be `capturedPendingSettlement` or `settledSuccessfully`. A mismatch answers 409 and leaves the order `pending`.
- The mark-paid write is conditional: `UPDATE store_orders SET status='paid', transaction_id=? WHERE id=? AND status='pending'`. A replayed notification therefore changes nothing, and the unique index on `transaction_id` is a second guard.
- For the webhook to exist in production, the endpoint URL has to be registered in the Authorize.Net merchant interface and Authorize.Net's servers have to be able to POST to the public storefront. Neither fact is in the repo (sections 2 and 6).

### 0.6 What the tests prove today, and what they cannot

tests/commerce.cjs drives the real dispatcher against a fake D1 and a stubbed `fetch` that answers only the two Authorize.Net request shapes; the tax contract is never called. Verified coverage includes: the demo answer from `/api/payment/config` with an empty environment, the 401 and 403 guards, tampered client prices ignored, fabric taken from the server catalog, idempotent retries reusing one order, changed-bag and paid-order replays refused, profile and gift validation, cross owner order reads refused, webhook invalid signature 401, amount mismatch 409 with the order left pending, a correct webhook marking the order paid, webhook replay harmless, and the Wave 5 cookie owner cases.

Two structural limits, both load bearing for section 4:

- The suite's environment has no `ANET_ENV`, so every checkout case runs in sandbox mode. The live branch (shipping, the tax quote call, its validation, and the `COMMERCE_APPROVED` gate) has no coverage at all: the stubbed fetch throws on any request that is not one of the two Authorize.Net shapes, so a live mode checkout cannot even be expressed in the harness today.
- The webhook test signs its payloads with Node's `createHmac` using the same key construction the dispatcher verifies with. Test and code agree with each other by construction. Whether they agree with Authorize.Net is a fact about the provider that only a real sandbox notification can settle.

No evidence in the repo shows a real Authorize.Net account, sandbox or production, has ever been used with this code. Whether one exists is unverified (section 6).

## 1. Findings: what real money raises that demo mode hides

- **F1, the live totals path has never run.** Shipping and tax are computed only inside the live branch, which no test reaches and no deployment has ever armed (the deployed site reports demo). The first live checkout, sandbox proof included, cannot exercise it either, because sandbox mode skips the branch entirely. Consequence: the plan's sandbox proof step proves the payment path but not the totals path. Package 6.0 closes this in the harness before any credential exists, and the go live package (6.5) includes a supervised first live configuration check, because there is no sandbox that behaves like production for totals.
- **F2, real checkout requires an identity today.** With payment ready, a request with neither an app session nor the gateway identity gets 401 "Please sign in to continue." A guest with a bag cannot pay. Whether an ordinary shopper on the public site carries a gateway identity is platform behavior, unverified from the repo. Two honest launch shapes exist: launch real checkout together with accounts (which needs the Wave 5 package 5.3 email settings so shoppers can register), or build a guest checkout path, which is a design change to order ownership and order read security, not a setting. The owner picks in section 2; package 6.2 sizes the guest path if chosen. Until one of them happens, turning on production settings would show shoppers a secure checkout button that ends at a sign in error.
- **F3, the reviewed total is not the charged total in live mode.** The shopper reviews a merchandise subtotal on suits.me, then first sees shipping and tax on the provider's page, where the amount charged is the order total. The README documents this shape, and the review copy discloses it ("Calculated before payment"), but it is still the weakest point in the journey: a shopper can feel the price changed at the last step. The server already computes shipping and tax before creating the order, so surfacing both lines and the full total on the review step, before the redirect, is a small client and contract change. It is packaged in 6.1 as the recommended default; keeping the hosted page disclosure instead is the owner's call in section 2.
- **F4, webhook trust is proven only against itself.** The verification code and its test share one assumption about how the signature key becomes HMAC key bytes (the UTF-8 bytes of the 128 character hex string). If Authorize.Net signs with a different construction, every real notification fails verification, orders stay `pending`, and the shopper's return page sits at "being confirmed" while the money has moved. Nothing in the repo can settle which construction the provider uses. The sandbox proof gate (package 6.3) therefore requires a real notification generated by Authorize.Net's sandbox, not a locally signed one, and treats a signature failure there as a stop, not a surprise to debug in production.
- **F5, a paid order currently goes nowhere.** The complete staff facing surface for orders is: nothing. No notification email (commerce sends no email; the only mail code in the repo is the Wave 5 account mailer), no orders view for the shop, no export, no refund, void, or cancellation path anywhere (no provider call, no status, no screen; verified by searching lib/, app/, and the client scripts), no status beyond `pending` and `paid`, and no fulfillment state at all. The only readers of `store_orders` are the owner's own order reads. On top of that, checkout today displays a delivery estimate of about 1 week (DELIVERY_ESTIMATE_WEEKS in public/app.js, shown in the checkout summary), which becomes a real promise the moment real orders exist. Section 2 asks the owner how a paid online order reaches the shop floor alongside the in person orders the physical shop already works from, and to confirm or correct the delivery estimate. Package 6.4 implements the chosen handoff.
- **F6, gift cards can be sold but never delivered or redeemed.** Checkout validates and prices gift cards, and in live mode would charge real money for them. No code delivers a gift card to its recipient (the client copy still says demo gift cards do not create redeemable credit or send email), and no code anywhere accepts a gift card as payment. Selling them live as things stand would take money for a product that does not function. The owner picks in section 2: exclude gift cards from live checkout at launch (a small gate in package 6.1), or fund delivery and redemption as its own package before they are sold.
- **F7, the server catalog is the price of record, and the site calls its own prices illustrative.** Server side repricing is only as trustworthy as lib/catalog.json. The storefront's own copy says "Product specifications and prices are illustrative in this design preview" (collection pages) and the FAQ says garment names, fabrics, pricing, and production details "must be matched to the business catalog before live selling." Wave 3 option pricing was captured deliberately and is consistent between client and server, but the base catalog was never confirmed as the merchant's real selling prices. Section 2 asks the owner to confirm the catalog, or name the confirmed subset for launch. Engineering does not change prices in this wave.
- **F8, smaller hardening items, all verified in code.** (a) `ANET_ENV` accepts anything: a typo silently selects sandbox endpoints and sandbox mode, including with production credentials present. Package 6.0 makes an unrecognized value refuse readiness instead of guessing. (b) Tax validation rejects a quote above the merchandise subtotal; if the owner's tax approach ever needs tax on shipping to push the figure higher relative to a discounted subtotal, that bound needs revisiting with the owner, not silently. (c) Duplicate protection is per checkout attempt: the idempotency key lives in one browser's local storage, so the same shopper on a second device, or after clearing storage, generates a new key and a second payable order for the same bag. Each order is individually legitimate; the protection stops double charging for one attempt, not double buying across attempts. Customer care copy should not promise more than that. (d) Abandoned `pending` orders never expire and are never cleaned up; they accumulate harmlessly but forever, and a stale pending order keeps its idempotency key answering replays. Package 6.1 adds an expiry rule for unpaid pending orders. (e) Delivery addresses are US only by validation; international shoppers cannot complete a live checkout. That is a launch scope fact, recorded here so it is a decision and not a discovery.
- **PCI posture.** The hosted form shape means card numbers never enter suits.me systems, which is the smallest exposure a hosted integration offers. The merchant's exact self assessment obligations are a question between the owner and Authorize.Net or their acquirer; nothing in the repo answers it, and it is listed in section 6 rather than asserted here.

## 3. Design decisions taken in this document (no owner input needed)

- Keep the Accept Hosted shape and `authCaptureTransaction`. The integration's security posture (no card data on suits.me systems, provider re-fetch on the webhook, amount equality, conditional status write) is sound as built; the wave's work is proof, totals, and handoff, not a rebuild.
- Keep the webhook as the only writer of `paid`. The return page observes; it never asserts payment.
- Keep demo mode exactly as it is until the go live package. Demo labelling comes off only in the same change that arms production, per the CHK-01 acceptance criteria, and the client copy that switches on `paymentConfig.ready` already does most of that work (section 4, package 6.5 enumerates the static labels that remain).
- Sandbox before production, with the proof as a hard gate: packages that need no owner inputs go first, the sandbox proof runs on sandbox credentials only, and production values are touched only in package 6.5 after the owner decides.
- No real order is ever placed by engineering on the production account. The first live transaction is the owner's own, made or authorized by the owner after go live configuration is verified.

## 5. Test strategy

- Per package: the full `pnpm test` chain (23 suites at the start of this wave) and the root `pnpm build` pass in the package worktree, with results stated in the PR and to the owner, per the standing rules. No package weakens an existing assertion; the commerce suite's header and cookie owner cases from Wave 5 are part of the floor.
- Harness journeys, wired into the test chain: **J27** (6.0) live mode totals and gates against the stubbed tax service, including refusal of a tax quote that is negative, fractional, or above the subtotal, and demo mode persisting when any production ingredient is missing. **J32** (6.1) totals shown before redirect equal the stored order total, and an expired pending order refuses payment and is replaced on restart. **J33** (6.2, only if funded) a guest completes checkout and reads the order back with the guest credential, and cannot read another guest's order.
- Provider journeys, run as the 6.3 runbook against the Authorize.Net sandbox and recorded in this document, never in CI and never against production: **J28** successful sandbox payment to a `paid` order with the return page landing on the order; **J29** declined card and cancelled return leave one `pending` order, and the retry pays that same order; **J30** replaying a paid checkout and resubmitting a changed bag under one key are both refused; **J31** a genuine provider notification verifies and marks the order paid, and a notification whose amount does not match is refused with the order left pending.
- The rule from the brief stands throughout: no real order is placed, and no production credential is used, by engineering at any point in this wave. Sandbox cards and sandbox notifications only, until the owner's own first transaction after go live.

## 6. Unverified register

- Whether the business has any Authorize.Net account today, sandbox or production. Nothing in the repo shows one ever being used.

Public GET reachability of the deployed API routes was verified during Wave 5; provider POST delivery was not, and the implementation plan's handoff notes record that the earlier owner private site blocked external webhook senders.

- Whether the production database has the `store_orders` table applied. The build ships drizzle/0000_furry_hardball.sql in the deployment bundle; how and when the control plane applies migrations is platform behavior, the same open class carried in the Wave 5 register.

- Whether the merchant interface configuration sends customer receipt emails. The hosted settings in code enable the on page receipt only; email behavior is not in the repo.
